# Инструкции для AI-агентов

## 1. Назначение репозитория

Этот репозиторий содержит **официальный CLI и управляющий слой AI Development Harness**.

AI Development Harness — репозиторно-ориентированная система для управляемой разработки с AI-агентами. Требования, ADR, STEP, результаты проверок, аудиты и другие долговечные проектные артефакты остаются в Git-репозитории проекта. Сам Harness как продукт постепенно выносится из каждого проекта в отдельный устанавливаемый дистрибутив.

Задача этого репозитория — предоставить такой дистрибутив и детерминированный программный слой Harness:

- CLI `harness`;
- настройку, обнаружение и валидацию проекта;
- разрешение и обновление релизов Harness;
- миграции схемы проекта;
- движок протокола и машину состояний;
- детерминированные валидаторы и проектные сервисы;
- общий локальный API / интеграционный интерфейс для runtime-адаптеров, редакторских интеграций и других внешних инструментов.

Этот репозиторий **не является обычным проектом-потребителем Harness**. Здесь разрабатывается сам продукт Harness CLI.

## 2. Главная архитектурная граница

Не превращай CLI в обязательную терминальную обёртку над Claude Code или Codex.

Интерактивная сессия должна по возможности оставаться под управлением самой среды выполнения, чтобы штатно работали:

- запросы разрешений;
- подтверждения;
- вопросы пользователю;
- разрешения WebFetch и других инструментов;
- аутентификация;
- TTY-взаимодействие.

Концептуальная схема:

```text
Claude Code / Codex
        │
        │ команды протокола Harness
        ▼
интеграционный слой / локальный API Harness
        │
        ▼
Harness Core
  ├─ протокол
  ├─ валидаторы
  ├─ машина состояний
  └─ проектные сервисы
        │
        ▼
репозиторий проекта

Harness CLI
  ├─ setup
  ├─ update
  ├─ doctor
  ├─ validate
  ├─ migrations
  └─ локальные сервисы управляющего слоя
```

Runtime-адаптеры могут входить в Harness Core, но семантика протокола и оркестрации не должна зависеть от конкретного runtime.

## 3. Что принадлежит Harness, а что проекту

Одна из главных целей проекта — перестать копировать Harness Core внутрь каждого пользовательского репозитория.

В пользовательском репозитории должны оставаться прежде всего данные, принадлежащие проекту:

```text
harness.yaml
AGENTS.md
CLAUDE.md
docs/
planning/
src/
tests/
...
```

Отдельно должны поставляться общие компоненты Harness:

- реализация протокола;
- валидаторы;
- детерминированные инструменты;
- базовые skills;
- миграции;
- сервисы, независимые от runtime;
- runtime-адаптеры;
- неизменяемые релизы Harness.

Не возвращай новую архитектуру к обязательному хранению управляющего слоя внутри каждого проекта, например через новые зависимости на:

```text
.harness/tools/**
.harness/docs/**
```

Исключение допустимо только для явно описанной миграционной или compatibility-задачи.

## 4. Состояние и хранение

Конфигурация, принадлежащая проекту, хранится в `harness.yaml`.

Операционное состояние конкретного clone/worktree должно храниться вне отслеживаемого рабочего дерева. Для определения пути используй Git:

```bash
git rev-parse --git-path ai-harness
```

Концептуально это соответствует:

```text
.git/ai-harness/
```

Не складывай блокировки выполнения, кэши, временное runtime-состояние и другие clone-local данные в отслеживаемые файлы проекта.

Глобальные релизы, кэш и конфигурация Harness должны использовать системные кроссплатформенные пути, а не жёстко заданные Unix-only директории.

## 5. Источники истины

Для работы внутри этого репозитория используй следующий порядок:

1. текущий код, тесты и метаданные пакета — источник истины о фактически реализованном поведении;
2. `docs/PRODUCT_REQUIREMENTS.md` — канонический продуктовый контракт и нормативные требования;
3. `docs/ARCHITECTURE.md` — канонические архитектурные границы, ownership и dependency direction;
4. `docs/MIGRATION.md` — канонический контракт миграции legacy repository-embedded проектов;
5. `docs/ROADMAP.md` — канонический порядок реализации и последовательность архитектурной миграции;
6. `README.md` — обзор и навигация;
7. актуальный `main` репозитория `ai-development-harness/ai-development-harness-template` — эталон текущего поведения ещё не перенесённых частей протокола;
8. связанные issues, pull requests и проектные заметки.

Не копируй устаревшую реализацию из template механически. При переносе отделяй:

- контракт проекта;
- продуктовую логику Harness;
- операционное состояние clone/worktree;
- сгенерированные представления;
- поведение конкретного runtime-адаптера.

Если template и CLI осознанно расходятся из-за новой архитектуры, архитектура CLI имеет приоритет для кода этого репозитория.

## 7. Технические правила

Текущая техническая база:

- TypeScript;
- Node.js 20+;
- ESM;
- строгий режим TypeScript;
- Vitest;
- Commander;
- Zod;
- YAML.

Перед завершением изменения, когда это применимо, выполняй:

```bash
npm run typecheck
npm test
npm run build
```

При изменении поведения добавляй или обновляй тесты.

Предпочитай небольшие детерминированные модули вместо больших функций, одновременно смешивающих файловую систему, Git, parsing и представление данных.

Ошибки CLI должны быть понятны человеку и по возможности пригодны для будущего машиночитаемого API.

## 8. Версионирование

Версия npm/CLI имеет **один источник истины — `package.json -> version`**.

Не хардкодь номер версии CLI в исходном коде TypeScript, README или регистрации команд.

`harness --version` и любые другие программные потребители должны получать версию пакета из package metadata.

Не путай:

- **версию CLI-пакета**;
- **релиз Harness**, закреплённый конкретным проектом в `harness.yaml`;
- **версию схемы/миграции**.

Это разные области версионирования.

## 9. Детерминированность

Ключевой принцип Harness:

> Модель решает смысловые задачи; вычислимую, проверяемую и механическую работу выполняет детерминированный код.

Поэтому parsing, валидация, переходы состояний, миграции, Git safety, разрешение релизов и другие вычислимые операции должны реализовываться кодом, а не текстовыми инструкциями для AI.

Не добавляй LLM-рассуждение туда, где результат можно однозначно вычислить.

## 10. Совместимость и безопасность

CLI будет работать с реальными пользовательскими Git-репозиториями. Изменения setup/update/миграций должны быть консервативными.

- Не перезаписывай существующие файлы проекта без явной политики миграции.
- Не удаляй пользовательские данные как часть автоматического восстановления.
- Не выполняй разрушающие Git-операции по умолчанию.
- Миграция должна быть версионированной, проверяемой и по возможности идемпотентной.
- Не запускай произвольные scripts/hooks из устанавливаемого релиза Harness без отдельной доверенной модели выполнения.
- Обработка путей должна быть кроссплатформенной и не позволять выходить за ожидаемые границы.

## 11. Текущий объём и план

Первый реализованный срез намеренно небольшой:

- `harness setup`;
- `harness doctor`;
- `harness validate`;
- `harness status`.

Канонический план дальнейшей работы находится в `docs/ROADMAP.md`.

Перед любым существенным архитектурным изменением или изменением реализации:

1. прочитай `docs/ROADMAP.md`;
2. определи, к какому этапу относится изменение;
3. не реализуй будущий этап «заодно»;
4. если меняется принятая последовательность или архитектурная граница, сначала актуализируй план.

Не считай будущие пункты плана уже реализованными. Перед использованием возможности проверяй фактический код.

## 12. Стиль изменений

При проектировании изменений задавай вопрос:

> Эта логика принадлежит пользовательскому репозиторию или продукту Harness?

Если логика общая для всех проектов Harness, детерминирована и не является знанием конкретного проекта, по умолчанию ей место в Harness Core/CLI, а не в сгенерированных файлах каждого проекта.

Сохраняй CLI независимым от конкретного runtime, кроссплатформенным и пригодным как общий движок для других интеграций.

## 13. Язык документации

Документация, инструкции для AI-агентов, README, архитектурные документы и описания требований в этом репозитории пишутся на русском языке.

На английском сохраняются только:

- имена файлов и каталогов;
- команды CLI;
- идентификаторы требований и артефактов;
- имена API, типов, функций и параметров;
- код;
- официальные названия технологий и устоявшиеся технические термины, если перевод ухудшает точность.

Не смешивай русские и английские предложения без технической необходимости.
