# Инструкции для AI-агентов

## 1. Что это за проект

Этот репозиторий содержит **официальный CLI / управляющий слой AI Development Harness**.

AI Development Harness — это репозиторно-ориентированная система для управляемой разработки с AI-агентами: требования, ADR, STEP, reviews, audits и другие долговечные проектные артефакты остаются в Git-репозитории проекта, а сам Harness как продукт постепенно выносится из каждого проекта в отдельный устанавливаемый дистрибутив.

Задача этого репозитория — предоставить этот дистрибутив и детерминированный программный слой Harness:

- CLI `harness`;
- настройка, обнаружение и валидация проекта;
- разрешение и обновление релизов Harness;
- миграции схемы проекта;
- движок протокола / машина состояний;
- детерминированные валидаторы и проектные сервисы;
- общий локальный API / интеграционный интерфейс для редакторских интеграций, runtime-адаптеров и других внешних инструментов.

Этот репозиторий **не является обычным проектом-потребителем Harness**. Здесь разрабатывается сам продукт Harness CLI.

## 2. Главная архитектурная граница

Не превращай CLI в обязательную терминальную обёртку над Claude Code или Codex.

Интерактивная runtime-сессия должна по возможности оставаться у самого runtime, чтобы штатно работали:

- запросы разрешений;
- подтверждения;
- вопросы модели пользователю;
- разрешения WebFetch / инструментов;
- TTY UX;
- аутентификация конкретного runtime.

Концептуальная граница:

```text
Claude Code / Codex
        │
        │ протокол / интеграция Harness
        ▼
интеграционный слой / локальный API Harness
        │
        ▼
Harness Core
  ├─ протокол
  ├─ валидаторы
  ├─ машина состояний
  └─ проектные сервисы
        │
        ▼
репозиторию проекта

Harness CLI
  ├─ setup
  ├─ update
  ├─ doctor
  ├─ validate
  ├─ migrations
  └─ локальные сервисы управляющего слоя
```

Runtime-адаптеры могут появляться в Harness Core, но семантика оркестрации не должны зависеть от конкретного runtime.

## 3. Распределение ответственности между Harness и проектом

Один из главных смыслов этого проекта — перестать копировать Harness Core внутрь каждого пользовательского repository.

В пользовательском репозиторию проекта должны оставаться прежде всего данные, принадлежащие проекту:

```text
harness.yaml
AGENTS.md
CLAUDE.md
docs/
planning/
src/
tests/
...
```

Реализация, принадлежащая Harness должна поставляться отдельно:

- протокол implementation;
- валидаторы;
- deterministic tools;
- core skills;
- migrations;
- runtime-neutral services;
- immutable релиз Harnesss.

Не возвращай новую архитектуру к обязательному хранению реализации управляющего слоя внутри проекта, например через новые зависимости на:

```text
.harness/tools/**
.harness/docs/**
```

если это явно не требуется задачей миграции/совместимости.

## 4. Состояние и хранение

Конфигурация, принадлежащая проекту, хранится в `harness.yaml`.

Операционное состояние конкретного clone/worktree должен храниться вне отслеживаемого рабочего дерева через Git private path:

```bash
git rev-parse --git-path ai-harness
```

Концептуально это соответствует:

```text
.git/ai-harness/
```

Не складывай блокировки выполнения, кэши и временное состояние runtime и другие clone-local данные в отслеживаемые файлы проекта.

Глобальные релиз Harnesss/cache/config должны использовать платформозависимые системные пути, а не жёстко заданные Unix-only директории.

## 5. Источники истины

Для работы внутри этого репозитория используй следующий порядок:

1. текущий код, тесты и метаданные пакета этого repository;
2. `docs/ROADMAP.md` — канонический план работ и последовательность архитектурной миграции;
3. `README.md` и явно принятые архитектурные контракты этого repository;
4. актуальный `main` репозитория `ai-development-harness/ai-development-harness-template` — как reference текущего протокол behavior, пока соответствующий функционал ещё не перенесён в CLI;
5. связанные issues / pull requests / проектные заметки.

Не копируй устаревшую реализацию из template механически. При переносе отделяй:

- контракт проекта;
- продуктовую логику Harness;
- clone-local operational state;
- сгенерированные представления;
- поведение адаптеров конкретного runtime.

Если template и CLI уже расходятся из-за осознанной новой архитектуры, архитектура CLI имеет приоритет для кода этого repository.

## 7. Технические правила

Текущая техническая база:

- TypeScript;
- Node.js 20+;
- ESM;
- строгий TypeScript;
- Vitest;
- Commander;
- Zod;
- YAML.

Перед завершением изменения выполняй, когда применимо:

```bash
npm run typecheck
npm test
npm run build
```

Для изменения поведения добавляй или обновляй тесты.

Предпочитай небольшие детерминированные модули вместо больших функций, смешивающих работу с файловой системой, Git, parsing и представлением данных.

Ошибки CLI должны быть понятны человеку и по возможности пригодны для будущего машиночитаемого API.

## 8. Версионирование

Версия npm/CLI имеет **один источник истины — `package.json -> version`**.

Не хардкодь номер версию CLI в исходном коде TypeScript, логике README или регистрации команд.

`harness --version` и любые другие программные consumers должны получать package version из package metadata.

Не путай:

- **версия CLI-пакета**;
- **релиз Harness**, закреплённый конкретным проектом в `harness.yaml`;
- версия схемы/миграции.

Это разные области версионирования.

## 9. Детерминированность

Ключевой принцип Harness:

> Модель решает смысловые задачи; вычислимую, проверяемую и механическую работу выполняет детерминированный код.

Поэтому parsing, валидация, переходы состояний, миграции, Git safety и разрешение релизов и другие вычислимые операции должны реализовываться кодом, а не текстовыми инструкциями для AI.

Не добавляй LLM-рассуждение туда, где результат можно однозначно вычислить.

## 10. Совместимость и безопасность

CLI будет работать с реальными пользовательскими Git-репозиториями. Изменения setup/update/миграции должны быть консервативными.

- Не перезаписывай существующие project files без явной политики миграции.
- Не удаляй пользовательские данные как часть автовосстановления.
- Не делай разрушающие Git-операции по умолчанию.
- Миграция должна быть версионированной, проверяемой и по возможности идемпотентной.
- Не запускай произвольные scripts/hooks из устанавливаемого релиз Harness без отдельной доверенной модели выполнения.
- Обработка путей должен быть кроссплатформенной и не позволять выходить за ожидаемые границы.

## 11. Текущий объём и план

Первый реализованный срез намеренно небольшой:

- `harness setup`;
- `harness doctor`;
- `harness validate`;
- `harness status`.

Канонический план дальнейшей работы находится в `docs/ROADMAP.md`.

Перед любым существенным архитектурным изменением или изменением реализации обязательно:

1. прочитай `docs/ROADMAP.md`;
2. проверь, к какому этапу относится изменение;
3. не реализуй будущий этап «заодно»;
4. при изменении принятой последовательности или архитектурной границы сначала актуализируй план.

Не считай будущие пункты план уже реализованными. Перед использованием возможности проверяй фактический код.

## 12. Стиль изменений

При проектировании изменений задавай вопрос:

> Эта логика принадлежит пользовательскому репозиторию проекта или продукту Harness?

Если логика общая для всех проектов Harness, детерминирована и не является знанием конкретного проекта, по умолчанию ей место в Harness Core/CLI, а не в сгенерированных файлах каждого проекта.

Сохраняй CLI runtime-neutral, кроссплатформенной и пригодным как общий движок для других интеграций.


## 13. Язык документации

Документация, инструкции для AI-агентов, README, архитектурные документы и описания требований в этом репозитории пишутся на русском языке.

На английском сохраняются только:

- имена файлов и каталогов;
- команды CLI;
- идентификаторы требований и артефактов;
- имена API, типов, функций и параметров;

- официальные названия технологий и устоявшиеся технические термины, если перевод ухудшает точность.

Не смешивай русские и английские предложения без технической необходимости.
